• For SQL injection specifically, the contact form is protected by parameterized PostgreSQL queries in marlette/app.js:132. The insert uses VALUES ($1, $2, $3, $4, $5, $6, $7) and passes user input as a separate values array, so
  firstName, email, message, etc. are not concatenated into raw SQL. That is the main SQL-injection defense here.

  There are also non-SQL abuse controls on the same route: IP rate limiting in marlette/app.js:73, a honeypot field in marlette/views/contact.ejs:31, and reCAPTCHA verification in marlette/app.js:115 with the client token setup in
  marlette/views/partials/header.ejs:78.

  What is not there:

  - No server-side validation/sanitization for field length, format, or allowed values beyond HTML form attributes.
  - No SQL risk from that omission because the query is parameterized, but it does leave room for bad data quality.
  - User input is interpolated directly into the notification email HTML in marlette/app.js:159, which is a separate HTML/content-injection concern, not a SQL-injection one.

  So the short answer is: SQL injection protection is present and correctly implemented for the contact form’s database insert. The bigger gaps are input validation and safe HTML escaping in the email body.

  The problem is the submission detail modal. It fetches raw submission JSON from marlette/app.js:332 and then builds an HTML string with untrusted fields such as sub.email, sub.phone, and especially sub.message, before assigning it with
  contentEl.innerHTML = html in marlette/views/admin-dashboard.ejs:146. If someone submits something like <img src=x onerror=alert(1)> in the message field, that can execute when an admin opens the modal. That is classic stored XSS.

  issue than site XSS, but it is still unsafe content handling.

  So the short answer is: partially mitigated, but not fully. The table view is escaped; the admin modal is vulnerable to stored XSS. If you want, I can patch that by rendering the modal with textContent/DOM node creation instead of
  innerHTML, and add basic output hardening.

• I’ve isolated the main issues. One of them is more serious than the contact form itself: a reusable invite token can be turned into repeated account takeover for an admin within the token lifetime. I’m cross-checking the exact exploit
  path before I summarize.

• Explored
  └ Read app.js

──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

• Findings:

  1. High: stored XSS in the admin submission modal. Untrusted submission fields are returned as JSON from marlette/app.js:331 and then injected into innerHTML in marlette/views/admin-dashboard.ejs:146. A contact form payload in message,
     email, or phone can execute when an admin opens the modal.

  2. High: invite tokens are reusable and can reset an existing admin’s password repeatedly until expiry. The signup flow verifies the token, then does INSERT ... ON CONFLICT DO UPDATE on admins in marlette/app.js:508, but it never
     deletes or invalidates the invite token afterward. That means any valid invite link can be reused for up to 48 hours to take over that admin account again.

  3. High: password-reset and invite links are built from the request Host header in marlette/app.js:244, marlette/app.js:421, and marlette/app.js:467. An attacker can submit a reset request with a forged host so the emailed link points
     to an attacker-controlled domain while still carrying the real token. That is a classic host-header poisoning / password-reset poisoning issue.

  4. Medium: there is no CSRF protection on admin state-changing routes. POST /admin/delete, POST /admin/highlight, POST /admin/invite, POST /admin/reinvite, and POST /admin/delete-admin rely only on the session cookie in marlette/
     app.js:324, marlette/app.js:364, marlette/app.js:408, marlette/app.js:448, and marlette/app.js:540. There are no CSRF tokens, no Origin/Referer checks, and no explicit sameSite cookie setting in the session config at marlette/
     app.js:21.

  5. Medium: admin sessions are not regenerated after login or signup. The code just sets req.session.admin = true in marlette/app.js:206 and marlette/app.js:528. That leaves the app open to session fixation if an attacker can cause a
     victim to use a known pre-auth session ID.

  6. Medium: session protection is weak by default. The app falls back to a hardcoded session secret in marlette/app.js:29, and the cookie config in marlette/app.js:32 does not explicitly set secure, httpOnly, or sameSite. httpOnly
     defaults to true in express-session, but secure and sameSite should be explicit for admin auth.

  7. Medium: admin login has no rate limiting or lockout. POST /admin/login in marlette/app.js:193 can be brute-forced indefinitely, while only the public contact form has a limiter at marlette/app.js:76.
  8. Low: the forgot-password flow leaks whether an admin email exists. It renders a different result for known vs unknown addresses in marlette/app.js:229 and marlette/app.js:263, which enables account enumeration.
  9. Low: exported CSV is vulnerable to spreadsheet formula injection. Contact form fields are written directly into CSV in marlette/app.js:352. If a field starts with =, +, -, or @, opening the CSV in Excel or Sheets can trigger formula
     execution.

  10. Low: database error details are exposed to authenticated users on the admin users page. marlette/app.js:393 sends e.message back to the browser. That is information leakage rather than a direct exploit.

  Open questions / assumptions:

  - I’m assuming this is internet-facing and that /admin/forgot-password is publicly reachable. If it is disabled externally, the host-header poisoning finding becomes less relevant.
  - I did not inspect deployment config outside this repo, so TLS termination, proxy behavior, and database network layout could raise or lower the practical impact of the session and DB transport issues.

  Short version: yes, there are several security issues outside SQL injection, and the two I would fix first are the stored XSS in the admin modal and the reusable invite-token flow. After that, fix reset/invite URL construction, add CSRF
  protection, and harden session handling.
